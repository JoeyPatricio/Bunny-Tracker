# Stretch Goals: Pi Migration, Water Tracking, and the Paper

Status as of 2026-07-24: **nothing here has been built.** No Pi 5 has been
bought, no sensors ordered, no code written. This is a plan.

Rewritten 2026-07-24 for the Python backend. The previous version assumed the
Node/Express server and the browser-trained TensorFlow.js MobileNetV2
classifier, both of which were deleted in the Node-to-Python port (see
`notes/architecture.md`). Every assumption about runtimes, dependencies, and
inference speed below has been re-derived against the code that exists now.

## Goal

Three deliverables.

1. The whole BunnyCam stack (FastAPI server, capture agent, Cloudflare tunnel,
   and n8n if it survives) runs 24/7 on a Raspberry Pi 5. Done looks like: the
   Windows PC is shut down, https://bunny-tracker.app loads from anywhere, the
   live stream works, a bunny moving overnight produces a clip in the gallery,
   and an alert email arrives.
2. Water intake and room environment tracking. Done looks like: the dashboard
   shows the current bowl level, today's intake in ml with a 7-day trend, and
   the room's temperature and humidity with daily min/max. An email arrives
   when the bowl runs low, when daily intake drops well below the rabbits'
   own baseline (an early GI stasis signal), or when the room gets hot
   (rabbits cannot sweat; heat stress starts around 28C).

3. A research paper describing the system and what building it actually
   measured. Done looks like: a finished preprint, its figures and tables
   generated by scripts in this repo from a frozen set of artifacts, every
   number in it reproducible by someone who clones the repo, and a released
   dataset that does not require publishing video of the inside of the house.

Phase A (migration) comes first: the water sensor wires into the Pi's GPIO,
which the PC does not have. Phase C (the paper) is independent of both and can
start any time, though it gets a better latency section after Phase A.

## Non-goals

- **No classifier improvement work.** The deployed model is currently less
  accurate than the tfjs one it replaced (61.5% vs 74.4% held out,
  `notes/architecture.md` debt item 1). That is a data-volume problem waiting
  on more labeled clips, it is tracked there, and it does not block or change
  anything in this plan. The Pi runs whatever ONNX artifacts exist at
  migration time. Phase C runs *measurement* experiments (repeated splits,
  ablations, a learning curve) offline on cached embeddings; those characterize
  the model, they do not try to fix it, and nothing they produce gets deployed.
- **No training on the Pi.** `.venv-train` (torch, timm) is dev-box only.
  Retraining stays a thing that happens on the PC, or on whatever machine
  replaces it, and ships ONNX files to the Pi.
- No vision-based "drinking" behavior class in this round. The load cell
  covers water; a drinking class can be layered on later.
- No multi-camera support.
- No database. Water data uses the project's existing file-based storage
  pattern.
- No port of the Windows autostart .bat.

## Assumptions and decisions

- **Hardware to buy** (one order, ~$170-200 total):
  - Raspberry Pi 5, 8GB (n8n alone idles at ~400MB; 8GB leaves headroom)
  - Official active cooler and 27W USB-C PSU (sustained encode plus inference
    will throttle a passively cooled Pi)
  - Case, and **storage sized for write churn, not capacity** (see the next
    bullet): a USB3 SSD, or an NVMe HAT plus a small NVMe drive, in preference
    to a microSD. If it has to be a card, high-endurance A2, 128GB.
  - 5kg strain-gauge load cell + HX711 breakout board + female-female jumper
    wires (~$10)
  - BME280 temperature/humidity sensor breakout, I2C version (~$5-8), plus
    30cm+ of wire so it can sit at rabbit level away from the Pi's own heat
  - Heavy ceramic bowl if the current one is light, plus two small rigid
    plates (plywood or acrylic) and M4/M5 standoffs to sandwich the load cell
  - The onn 4K USB webcam moves to the Pi; no Pi camera module needed.
- **Write churn is the real storage constraint, and it is larger than it
  looks.** The agent writes continuously, around the clock, in two places that
  are not the recordings gallery: the rolling 12s segments (libvpx at 1Mbit/s,
  roughly 10GB/day, pruned every 60s) and the live-view JPEG, rewritten 12
  times a second (20-40KB each, on the order of 30GB/day to a single path).
  Neither is data anyone keeps. On a microSD that is a card-killing workload;
  the fix is to put both on tmpfs (`/dev/shm`) so they never touch persistent
  storage, and it needs a small code change (see step 3), since
  `agent/capture.py` currently hardcodes both paths under the repo.
- **OS**: Raspberry Pi OS Lite **64-bit** (Bookworm). The 64-bit image is not
  optional: onnxruntime ships aarch64 wheels and no armhf ones, so a 32-bit
  install means building it from source. Bookworm's default Python is 3.11.2,
  which matches onnxruntime's cp311 wheel exactly (researched in
  `notes/environment.md`, not yet confirmed on hardware).
- **Inference is ONNX Runtime on the CPU execution provider**, running
  `server_py/models/backbone_int8.onnx` and `head.onnx`. No torch on the Pi,
  ever: `requirements.txt` is the runtime list and deliberately excludes it.
  The dev-box benchmark is about 5.8ms per step (int8 backbone plus head)
  against a 1500ms frame budget, so there is roughly 250x of headroom to lose
  to a slower CPU before this becomes a problem. `scripts/bench_pi.py` exists
  precisely to turn that guess into a number on real hardware, and it takes a
  minute to run.
- **Node is now optional on the Pi.** The backend is Python; the client is
  prebuilt static files. Node is needed only for n8n (droppable, see step 7)
  and for `npm run build`, which can happen on the PC with only `client/dist/`
  copied over.
- **Process supervision moves to systemd, not pm2.** This is a change from the
  earlier version of this plan. pm2 is a Node process manager, and once the
  backend is Python and n8n is optional, keeping pm2 means installing a whole
  Node runtime to supervise two Python processes and cloudflared. systemd is
  already running on Bookworm, handles restart-on-failure and boot ordering
  natively, and drops pm2's documented footgun where `pm2 stop` is treated as
  a crash and relaunches the process (`notes/environment.md`). Cost: unit
  files instead of `ecosystem.config.cjs`, and `journalctl -u` instead of
  `pm2 logs`. If n8n stays and Node is on the box anyway, `pm2` remains a
  defensible fallback, but do not install Node solely to keep it.
- **ffmpeg**: Debian's apt package on the Pi. No code change needed;
  `agent/capture.py` already resolves `FFMPEG_PATH` first and falls back to
  the `imageio-ffmpeg` bundled binary, and `shared/frames.py` uses the
  imageio-ffmpeg copy only for offline frame extraction (a training-side
  concern that does not run on the Pi).
- **Camera input needs a v4l2 branch.** `agent/ffmpeg_io.py` pins format,
  resolution, and framerate only when `CAMERA_FORMAT == "dshow"`. Under v4l2
  nothing is pinned, so ffmpeg takes whatever the webcam offers by default,
  which is the exact failure class the Windows pinning exists to prevent
  (uncompressed 4K saturating the input buffer until motion detection sees a
  frozen scene). Step 3 adds the v4l2 equivalent.
- **Sensor reader is a separate process**, `server_py/sensor/water_sensor.py`,
  talking to the server over the same HTTP API everything else uses. Its GPIO
  dependencies (`RPi.GPIO`/`lgpio`, an HX711 library, `smbus2`) go in a
  **`requirements-pi-sensor.txt`**, not in `requirements.txt`: those packages
  do not install on the Windows dev box, and the project already keeps runtime
  and training dependencies in separate files for exactly this reason.
- **Sensor auth is its own credential.** `WATER_SENSOR_SECRET` in `.env`,
  checked with `hmac.compare_digest` in `app/auth.py` alongside the existing
  `is_agent_authed()`, entirely separate from the human session store and the
  login rate limiter. This follows the precedent the port established with
  `AGENT_TOKEN`: a headless process on your own network gets its own
  credential path so its failures can never lock out the human.
- **Water data storage**: append-only JSONL, one file per month
  (`server/water/YYYY-MM.jsonl`). Deliberately **not** `app/lib/json_store.py`,
  whose read-modify-write-whole-file pattern is right for a small map of
  labels and wrong for 2,880 appends a day: it would rewrite the entire month
  file on every reading.
- **Tunnel migrates, not recreated**: copy the existing cert and tunnel
  credentials to the Pi so DNS and the tunnel ID stay untouched.
- **Calibration**: 1g of water = 1ml. Tare and scale factor set once with a
  known weight.
- **n8n on the Pi is optional.** It is one email fan-out workflow, and
  `agent/capture.py` already falls back to the server's built-in `smtplib`
  path (`POST /api/notify`) whenever `ALERT_WEBHOOK_URL` is unset. If n8n
  misbehaves on ARM, drop it, lose nothing but fan-out flexibility, and the Pi
  needs no Node at all.

## Steps

### Phase A: Pi migration

#### 1. Order hardware

Everything in the hardware list above, one order. Nothing else can start
until the Pi arrives, but step 3 (portability commits) can happen meanwhile.

#### 2. Base Pi setup

Flash Pi OS Lite **64-bit** with SSH enabled (Raspberry Pi Imager sets user +
wifi). Confirm the architecture before going further, because the wheel story
depends on it:

```bash
uname -m    # must print aarch64
python3 -V  # expect 3.11.2 on Bookworm
```

Then:

```bash
sudo apt update && sudo apt install -y ffmpeg git python3-venv python3-dev
git clone <repo> ~/BunnyTracker && cd ~/BunnyTracker/server_py
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
```

**Verify:** `pip install` pulled a prebuilt onnxruntime wheel with no source
build, and:

```bash
.venv/bin/python -c "import onnxruntime, fastapi; print(onnxruntime.get_available_providers())"
```

prints a provider list including `CPUExecutionProvider`. Then confirm the
camera exposes MJPEG at 720p:

```bash
ffmpeg -f v4l2 -list_formats all -i /dev/video0
```

lists `mjpeg` at `1280x720`.

#### 3. Portability commits (on the PC, can run in parallel with shipping)

Three small changes, committed and verified on Windows before the Pi work
depends on them. (The old plan's ffmpeg-path override and its "remove orphaned
tfjs deps" item are both already resolved: `FFMPEG_PATH` is honored in
`agent/capture.py`, and `server/package.json` no longer exists.)

- **v4l2 input pinning** in `agent/ffmpeg_io.py::_build_args()`: add an
  `elif self.camera_format == "v4l2"` branch passing
  `-input_format mjpeg -video_size $CAMERA_SIZE -framerate $CAMERA_FPS`, the
  v4l2 spelling of what the dshow branch already does. Reuses the existing
  `CAMERA_SIZE`/`CAMERA_FPS` env vars, so no new configuration.
- **Path overrides for the transient writes**: `agent/capture.py` hardcodes
  `self.seg_dir` and `self.live_frame_path`. Read each from an env var with
  the current value as the default (`AGENT_SEGMENT_DIR`,
  `AGENT_LIVE_FRAME_PATH`), so the Pi can point both at `/dev/shm/bunnycam/`
  and Windows keeps behaving exactly as it does today.
- **systemd units** in `deploy/pi/`: `bunnycam-server.service` (runs
  `server_py/.venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port
  3001`, `WorkingDirectory=server_py`), `bunnycam-agent.service`
  (`-m agent.capture`), `bunnycam-tunnel.service`, and a
  `bunnycam-water.service` left disabled until Phase B. Each with
  `Restart=always`, `RestartSec=5`, and `After=network-online.target`. The
  agent unit needs `TimeoutStopSec` long enough for its graceful ffmpeg
  shutdown (10s is plenty) so systemd does not SIGKILL it and orphan ffmpeg,
  which is the Linux version of the camera-lock problem documented in
  `notes/environment.md`.

**Verify:** on Windows, `pm2 restart all`, dashboard loads, agent log shows
normal frame lines with unchanged motion values. Nothing regressed.

#### 4. Performance spike on the Pi

Two measurements, cheapest first.

**4a. Synthetic benchmark.** From `server_py/` on the Pi:

```bash
.venv/bin/python -m scripts.bench_pi
```

This reports per-step latency for the int8 backbone and the head against the
1500ms frame budget. On the dev box it is about 5.8ms. Anything under ~200ms
on the Pi means inference is a non-issue and the rest of this step is a
formality. (The script currently prints a "dev-box only" disclaimer; update
that wording once it has run on real hardware, since this is the run it was
written for.)

**4b. Live run.** Point the Pi agent at the still-running PC server: a Pi-local
`server/.env` with `AGENT_SERVER_URL=http://<pc-ip>:3001`, the same
`AGENT_TOKEN` as the PC, `CAMERA_FORMAT=v4l2`, `CAMERA_INPUT=/dev/video0`,
`FFMPEG_PATH=/usr/bin/ffmpeg`, and the two tmpfs path overrides from step 3.
Run `.venv/bin/python -m agent.capture` for 30 minutes.

Measure:

- Frame log lines hold the 1.5s cadence. The `busy` flag in
  `ffmpeg_io.py::_read_frames()` silently drops frames when inference is slow,
  so stretched spacing is the symptom of "too slow", not an error message.
- `top`: ffmpeg plus python comfortably inside the 4 cores. libvpx encoding,
  not inference, is the likelier hog.
- `vcgencmd measure_temp` stays under 80C sustained.

Fallback ladder if it is too slow, in order: confirm the int8 backbone is
actually the one loaded (`agent/capture.py` loads `backbone_int8.onnx`, but
check the log line at boot); cap onnxruntime's thread count so it stops
fighting ffmpeg for cores (`SessionOptions.intra_op_num_threads`); classify
every k-th frame while still embedding every frame into the ring buffer (the
two-stage split exists to make this cheap); drop the segment encode to a lower
bitrate or resolution; last resort raise `AGENT_FRAME_SECONDS` to 2-3, noting
that the 8-frame window then spans 16-24s instead of the ~12s the head was
trained on, which is real accuracy degradation, not a free knob.

**Verify:** steady cadence in logs, and a hand wave in front of the Pi's
camera saves a clip that appears in the PC server's gallery.

#### 5. Move the server and its data

Copy from PC to Pi:

- `server/`: `recordings/`, `labels.json`, `autolabels.json`, `hidden.json`,
  `monitor.json`, `activity-log.json`, `backups/`, `model/`, and `.env` (with
  the Pi camera/ffmpeg/path lines from step 4).
- `server_py/models/`: `backbone_int8.onnx` and `head.onnx`, the artifacts the
  agent actually loads. The `cache/` subdirectory is training scratch and does
  not need to travel.
- `client/dist/`: build it on the PC (`cd client && npm run build`) and copy,
  or install Node on the Pi and build there. Copying is preferable if n8n is
  being dropped.

Do **not** copy `.venv`. Virtualenvs embed absolute paths and platform-specific
binaries; the Pi's was built in step 2.

Install the systemd units, `systemctl enable --now bunnycam-server
bunnycam-agent`.

**Verify:** `http://<pi-ip>:3001` shows the dashboard with the full old
recording gallery, live feed streams, login works, and the agent uploads a
motion clip end to end on the Pi alone.

#### 6. Move the Cloudflare tunnel

Install arm64 cloudflared from Cloudflare's apt repo. Copy
`C:\Users\joepa\.cloudflared\cert.pem` and the tunnel credentials JSON
(`<tunnel-id>.json`) to `~/.cloudflared/` on the Pi. Stop the tunnel process
on the PC, `systemctl enable --now bunnycam-tunnel` on the Pi.

**Verify:** https://bunny-tracker.app loads from a phone on cellular while
the PC's tunnel process is stopped. Also confirm login still works through the
tunnel, since `app/security.py::get_client_ip()` reads the first
`X-Forwarded-For` hop and the rate limiter depends on it.

#### 7. Move n8n, or drop it

Dropping it is the cheaper answer and removes the last reason to install Node
on the Pi. To drop: leave `ALERT_WEBHOOK_URL` unset in the Pi's `.env` and
`agent/capture.py` routes alerts to `POST /api/notify`, which sends mail
through `smtplib` using the existing `EMAIL_*` settings.

To keep it: `sudo npm i -g n8n` (NodeSource Node 22), export the workflow and
credentials from the PC's n8n UI, and copy the `encryptionKey` from the PC's
`~/.n8n/config` (without it, imported credentials cannot decrypt). Run it
under systemd with the same env block the ecosystem file uses, and fix
`N8N_RESTRICT_FILE_ACCESS_TO`, which still points at the pre-rename
`Desktop\PetCam\server\recordings` path (`notes/architecture.md` debt item 4)
and would be wrong on the Pi regardless.

**Verify:** force a motion event; either n8n's execution log shows a run, or
the agent log shows `✉ Email: sent`. Mail lands at the hotmail address.

#### 8. Autostart, burn-in, decommission

`systemctl enable` each unit, then reboot the Pi and confirm everything comes
back unattended. Kill the PC stack (`pm2 kill`) and remove
`start-bunnycam.bat` from Windows startup, but keep the PC checkout intact for
two weeks as rollback. Burn in for a week: check `systemctl status`,
`journalctl -u bunnycam-agent --since -1h` for restart loops, temps, and disk
usage a few times.

**Verify:** after a Pi reboot with the PC off, the public site is live and a
real bunny clip is captured overnight without intervention. Check that
`/dev/shm` is holding segments and the live frame, and that persistent storage
is only growing at the rate of saved clips.

### Phase B: Water and environment tracking

#### 9. Wire the sensor and spike the data (riskiest step of Phase B)

Sandwich the load cell between the two plates, bowl on top. HX711 to GPIO:
VCC to 3.3V, GND to GND, DT and SCK to two free GPIO pins. Write
`server_py/sensor/read_hx711.py` as a throwaway: tare, calibrate the scale
factor against a known weight (weigh a full water bottle on a kitchen scale
first), then print grams once per second to a CSV. Let it log for 24 hours
with the rabbits living normally.

This spike answers the questions the real service depends on: baseline noise
and drift magnitude, what a drink looks like in the data, what a refill looks
like, and what a rabbit bumping or leaning on the platform looks like.

**Verify:** the 24h CSV shows drift under a few grams, at least one refill as
a clean positive step, drinking as small negative steps, and bumps as short
spikes that return to baseline within seconds.

#### 10. Sensor service

`server_py/sensor/water_sensor.py`: sample the load cell at 1Hz, keep a
30-sample rolling median (kills bump spikes), read the BME280 over I2C
(enable I2C via `raspi-config`; wire VCC/GND/SDA/SCL; no calibration needed),
and POST once per 30s to `POST /api/water/reading` as
`{ "grams": <n>, "tempC": <n>, "humidity": <n>, "at": <iso> }` with an
`X-Water-Secret` header. Dependencies go in `requirements-pi-sensor.txt`,
installed into the same `.venv`. Enable `bunnycam-water.service` from step 3.

Mount the BME280 near the rabbits' level, away from direct sun and at least
30cm from the Pi, which runs warm enough to skew a sensor sitting next to it.

**Verify:** `journalctl -u bunnycam-water -f` shows readings flowing with
plausible grams, tempC, and humidity; the server logs 200s; a wrong secret
gets 401; tempC roughly matches a household thermometer in the same spot.

#### 11. Server route and storage

`server_py/app/routers/water.py`, included in `app/main.py` alongside the other
routers and added to `GUARDED_PREFIXES` in `app/auth.py`:

- `POST /api/water/reading`: authorized by `X-Water-Secret` via a
  `is_water_sensor_authed()` helper next to `is_agent_authed()`, using
  `hmac.compare_digest`. Appends one JSON line to `server/water/YYYY-MM.jsonl`.
- `GET /api/water/summary` (admin-only, the default for any guarded path):
  current grams, today's intake ml, refill count, 7 daily totals, plus current
  tempC/humidity and today's min/max of each. Intake = sum of negative steps
  between readings, ignoring steps larger than a refill threshold in either
  direction. Refill = positive step over 100g. Tunable constants at the top of
  the file, informed by the step 9 spike data.

Note the auth ordering: `AdminGuardMiddleware` runs before the router, so the
new prefix must be added there or the POST returns 401 no matter what header
the sensor sends.

**Verify:** a script replays a synthetic day (baseline, 8 drinks of 10-20g,
one 300g refill, a few bump spikes) through the POST endpoint; the summary
reports intake within 10% of the known total and exactly one refill.

#### 12. Alerts

Checked in the reading handler, reusing the existing notification paths (the
n8n webhook with a `type: "water"` field if it survived step 7, otherwise the
`smtplib` path in `app/routers/notify.py`):

- Low level: current grams below `LOW_LEVEL_G` (default 150). At most one
  alert per 12h.
- Low intake: trailing 24h intake below 50% of the trailing 7-day daily
  average (needs 3+ days of data before arming). At most one per day. This is
  the health alert, so it is relative to the rabbits' own baseline, not an
  absolute number.
- High temperature: warning at `TEMP_WARN_C` (default 27), urgent at
  `TEMP_DANGER_C` (default 29), each at most once per 2h. Unlike the intake
  alert these are absolute thresholds; heat stress does not care what last
  week looked like. Optional low-temp warning (default 10) for winter.

Put the cooldown logic in one gate function that every water alert consults,
the way `notify.py`'s `alert_gate()` already does for behavior alerts. Two
parallel paths with their own cooldown copies is the exact bug the behavior
alerts had (`notes/fixes.md` 4.2, fixed during the port).

**Verify:** temporarily set `LOW_LEVEL_G` above the current level and
`TEMP_WARN_C` below room temperature; exactly one email arrives for each, and
a second does not within the cooldown.

#### 13. Dashboard panel

`client/src/components/WaterPanel.jsx` on the Camera tab (admin view only,
consistent with keeping live data off the public demo): current level as a
percentage of the last refill, today's intake in ml, a 7-day bar chart using
plain CSS bars in the existing style system (the project has no chart library;
do not add one for seven bars), and current temperature/humidity with today's
min/max.

**Verify:** panel numbers match `GET /api/water/summary`; refill the bowl and
the level updates within a minute; temperature updates after warming the
sensor in your hand.

### Phase C: The paper

#### 14. Decide what the paper claims, before running anything

This is the step that determines whether the rest is worth doing, so it comes
first and it is a writing step, not a coding one.

The claim this project can currently support is **not** "we built a more
accurate rabbit behavior classifier." It lost to its own baseline. What it can
support is a case study with a measured negative result:

> Continuous home animal monitoring on commodity hardware, built twice. On
> 184 clip-level labels across 5 behaviors, a frozen modern edge backbone with
> a learned temporal head (GRU over an embedding sequence) underperforms an
> older backbone with hand-designed mean/std window pooling, 61.5% vs 74.4%.
> We report the engineering that makes the comparison trustworthy (group-aware
> splitting by recording session, a two-stage streaming architecture, int8
> quantization that silently breaks on depthwise convolutions under per-tensor
> weight scaling), and characterize where the crossover between designed and
> learned temporal aggregation sits as a function of dataset size.

Write that paragraph, in your own words, before writing code. If the
experiments in step 15 do not survive contact with it, the claim changes, not
the experiments.

The alternative framing, worth a deliberate decision rather than drift: wait
until the labeled set is 2-3x larger, retrain, and write an accuracy paper
instead. That is a better paper if the retrain wins and a wasted year if it
does not. The negative-result version can be written now, and it is
publishable exactly because most people who hit this outcome never write it
down. Recommendation: write the current one; a future accuracy result is a
second paper, not a reason to delay the first.

Also decide the venue now, because it sets length and format: an arXiv
preprint (cs.CV or cs.LG) is the default and has no gatekeeper, and a
workshop on animal behavior/computer vision or on-device ML is the realistic
peer-reviewed target. Nothing in this project needs a full conference paper's
scope.

**Verify:** a one-paragraph claim and a named target venue exist in writing,
and every number in the claim traces to a file in `server_py/models/`.

#### 15. Run the experiments the claim needs

The current evidence is one split at one seed with 39 validation clips and
per-class support between 5 and 8. That is enough to make an engineering
decision and nowhere near enough to publish. Six experiments, roughly in order
of how much they change the paper's credibility. All of them run offline on
the cached embeddings in `server_py/models/cache/`, so they are minutes of
compute, not hours.

1. **Repeated group-aware splits.** `extract_frames.py --seed` and
   `train.py` already take the parameters; run 5 to 10 seeds and report mean
   and standard deviation, not a single number. With 39 val clips, a single
   split's accuracy moves several points on luck alone, and a reviewer will
   ask. Expect the gap to the baseline to survive this, and note that the JS
   baseline in `models/js_baseline.json` was measured on one split too, so it
   needs the same treatment or the comparison is not like-for-like.
2. **Learning curve.** Train both head architectures on 25%, 50%, 75%, and
   100% of the training clips, holding the val set fixed, and plot accuracy
   against dataset size. This is what converts "we believe it is a data
   problem" into evidence: if the mean/std curve is flattening while the GRU
   curve is still climbing, the crossover argument becomes a measurement
   instead of an opinion. This is the paper's most valuable figure.
3. **Head ablation on identical embeddings.** Single frame, mean pooling,
   mean+std pooling, 1D convolutional stack, GRU. `diagnose_meanstd.py`
   already implements the mean/std arm; the rest are variations on the same
   loop. Same backbone, same splits, same seeds, so the only variable is the
   aggregation.
4. **Backbone ablation.** Re-embed the same clips with a torch MobileNetV2
   from `timm` and rerun the head ablation on those embeddings. This
   disentangles "new backbone" from "new head", which is the confound the
   original result has. State plainly that the torch MobileNetV2 is not
   byte-identical to the tfjs one the live system used, so it is a controlled
   comparison of architectures, not a reproduction of the deployed baseline.
5. **Quantization table.** fp32, int8 per-tensor, int8 per-channel, each with
   accuracy and latency. The per-tensor result is a genuine finding worth a
   table row and a paragraph: MobileNet-family depthwise convolutions have
   per-channel weight ranges that one shared scale destroys, the accuracy
   collapse is silent, and per-channel recovers float32 exactly here.
6. **Latency.** `scripts/bench_pi.py` on the dev box now, on the Pi after
   Phase A. Report both, labeled by machine. If the Pi never happens, report
   dev-box numbers and say so; do not extrapolate to ARM in print.

Two things to fix while running these, both cheap and both things reviewers
poke at:

- **Confidence intervals.** With support of 5 to 8 clips per class, report
  Wilson intervals on per-class recall rather than bare percentages. A recall
  of 42.9% on 7 clips has an interval wide enough that the honest statement is
  "we cannot distinguish these classes at this sample size."
- **Label reliability.** Every label came from one annotator with no measured
  agreement. Re-label a random 40-clip subset blind, months after the
  originals, and report self-agreement. It is an afternoon of work and it
  turns an unstated assumption into a number.

**Verify:** every table and figure in the paper is emitted by a script in
`server_py/training/` or `server_py/scripts/` that reads from
`models/cache/` and writes to a `paper/figures/` directory. No number is typed
into the manuscript by hand.

#### 16. Freeze the artifacts the paper describes

A paper about a live system that keeps changing under it is unciteable. Before
writing prose, tag a commit, and copy into `paper/artifacts/`: the ONNX files,
`train_result.json`, `gate_result.json`, `js_baseline.json`, the manifest, and
the seed list. Every claim in the text cites one of those files.

If the model gets retrained during writing (a real possibility, since more
labels are the point of debt item 1), the paper describes the frozen artifacts
and says so with a date. It does not chase the deployment.

**Verify:** a fresh clone at the tagged commit, plus the frozen artifacts,
reproduces every number in the results section.

#### 17. Write it

Structure, with the sections that actually matter for this paper called out:

- **System description.** The two-stage streaming design and why it exists:
  the backbone runs once per frame, the head runs once per window step, and a
  single end-to-end graph over a sliding window would re-run the backbone N
  times per step for embeddings it computed a moment ago. The classical motion
  gate in front of the network, and why a hand-built detector still earns its
  place next to a CNN. This section writes itself out of `notes/learning.md`
  and `notes/architecture.md`.
- **Dataset.** 184 clips, 5 behaviors, one camera, one room, two rabbits,
  clip-level labels, class imbalance dominated by "normal". State the
  collection process honestly, including that high-motion low-confidence clips
  were preferentially retained for review, which is targeted collection of hard
  examples and also a sampling bias worth naming.
- **The weak-label problem.** The most interesting technical honesty in the
  project: labels are clip-level over roughly 12 seconds, but the behavior
  they name may occupy a fraction of the window. A "yawn" clip is mostly not
  yawning. The head is therefore trained on windows whose label is true of the
  clip but not of every window sampled from it. This is a multiple-instance
  learning setup being treated as ordinary supervised classification, it
  plausibly hurts the temporal head more than the pooling head (an ordering-
  sensitive model has more to lose from a mislocated event), and it is a
  legitimate future-work hook rather than a flaw to hide.
- **Results.** The tables and figures from step 15, with intervals.
- **Threats to validity.** Single environment, single camera, two animals,
  one annotator, small n, and the backbone-ablation caveat from step 15.4.
  Write this section early rather than last; it is the section that decides
  whether the paper reads as honest or as excuse-making, and drafting it early
  usually reveals an experiment worth adding.
- **Reproducibility and dataset release.** See step 18.

**Verify:** someone who has never seen the project can read the system section
and correctly describe the inference path. Run `/stop-slop` on the manuscript
before it goes anywhere.

#### 18. Release the artifact

The obvious blocker is that the raw data is video of the inside of a house.
The frozen-backbone design solves this almost for free: **release the cached
embeddings, not the video.** `models/cache/` holds `[T, 1280]` float arrays
plus `manifest.json` with labels and split assignments. Because the backbone is
frozen and never trains, those embeddings are sufficient to reproduce every
head-training result in the paper exactly, and they are not reconstructible
into recognizable images of the room.

Ship: the embedding cache, the manifest, the label file, the ONNX artifacts,
the training and evaluation scripts, and a README with the exact commands. Note
in the paper that the backbone ablation (step 15.4) cannot be reproduced from
the release alone, since it needs the source video to re-embed; that is an
honest limitation to state rather than paper over.

Do not release `.env`, recordings, or anything under `notes/`, which contains
machine-specific paths and is git-ignored for that reason.

**Verify:** unpack the release into a clean directory on a machine without the
recordings, run the documented command, and get the paper's headline numbers.

## Risks

1. **onnxruntime does not install cleanly on the Pi.** The aarch64 wheel story
   is desk research, not a device test (`notes/environment.md`). Step 2 checks
   it before anything is migrated, and it is a five-minute check. If the wheel
   is missing for the installed Python version, the escape hatch is a
   different Python minor version via pyenv or deadsnakes, not a source build.
2. **Inference or encoding too slow on the Pi.** Much lower risk than in the
   tfjs era: the model is int8 ONNX running on native code, benchmarked at
   ~5.8ms per step on the dev box against a 1500ms budget. Step 4 confronts it
   with a one-minute synthetic benchmark before any migration, and the
   fallback ladder is written. libvpx encoding is now the more likely
   bottleneck than the classifier.
3. **Storage write endurance.** Continuous segment encoding plus a 12fps
   live-view file rewrite is tens of GB per day of writes, most of it
   throwaway. Mitigated by moving both to tmpfs (step 3) and by preferring an
   SSD to a microSD. Left unaddressed, this is the failure that shows up three
   months in as mysterious corruption.
4. **Load-cell data too noisy for meaningful intake numbers.** Rabbits step on
   platforms and bump bowls; cheap load cells drift with temperature. The 24h
   raw-data spike (step 9) runs before any service code is written, the median
   filter and step detection are designed from that real data, and the health
   alert compares the rabbits against their own baseline so absolute accuracy
   matters less. If the spike shows the data is unusable, the fallback is
   level-only tracking (refill reminders, no intake), which the same hardware
   still supports.
5. **Credential migration snags (tunnel cert, n8n encryption key).** The PC
   stack stays intact and startable until the Pi passes burn-in, so rollback
   is `pm2 start` on the PC. n8n is explicitly droppable (step 7) since the
   email fallback is already wired into the agent.
6. **Camera defaults under v4l2.** Without explicit input pinning, ffmpeg
   negotiates whatever the webcam prefers, which on Windows meant uncompressed
   4K and a frozen inference feed. Step 3 adds the v4l2 pinning and step 4b's
   live run is where a wrong negotiation would show up, as a stretched frame
   cadence rather than an error.
7. **The negative result reads as "you did it wrong."** The obvious reviewer
   response to "the modern architecture lost" is that it was undertrained,
   badly tuned, or unluckily split. The defense is the experiments in step 15,
   in this order: repeated seeds kill the luck explanation, the learning curve
   supports the data-volume explanation, and the head ablation on identical
   embeddings kills the confound. Without those three, the paper is an anecdote
   and should not be submitted.
8. **Scope creep into a benchmark paper.** The pull is toward more backbones,
   more heads, more datasets, and a year of work. The scope that matches the
   evidence is one system, one dataset, one crossover question. If an
   experiment does not appear in the step 14 claim paragraph, it does not go
   in.
9. **Writing against a moving system.** Retraining on more labels is the whole
   point of debt item 1, and it will invalidate the results section if it lands
   mid-draft. Step 16 freezes tagged artifacts specifically so the paper can
   describe a dated snapshot while the deployment moves on.
